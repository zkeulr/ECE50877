\section{Related Work}
%-------------------------------------------------------------------------------

\subsection{Technical Report on a Virtual CTAP2 WebAuthn Authenticator~\cite{culnane2021virtualctap2webauthn}}

This technical report covers the development of the associated open source
Virtual CTAP2 WebAuthn authenticator. In addition to
a software only authenticator it also provides a proof of concept implementation
of a Trusted Platform Module (TPM) based authenticator, with associated
interfaces and libraries for using a TPM as the underlying credential store.
This project wants several improvements we hope to make.
First, the authors deliberately keep client-PIN verification outside
the TPM, reasoning that the PIN is typed
anyway so it "doesn't warrant" TPM protection. This is a waste of
modern TPMs' built-in dictionary-attack prevention, which we can enable.
Second, their authenticator uses a flat key hierarchy with no dictionary-attack
protection on the intermediate key. If we use passkey signing keys
as children of an intermediate PIN key that has a lockout policy,
then unlocking the PIN key makes them usable just as with Windows
Hello and we have brute force protection against the PIN.
Third, the paper notes that their method of emulating a USB HID device
is fragile. We can build the authenticator as a PAM module for
extensibility.
Finally, the authenticator suuports only ES256, which we could expand to
RSA and Ed25519.

\subsection{Securing FIDO2 Credentials Using Intel SGX~\cite{matos2026securing}}
This paper builds a centralized, replicated FIDO2
credential manager similar to the one we're building,
using /dev/uhid to emulate a USB HID FIDO2 device like
tpm-fido/VirtualWebAuthn does.
Their conclusion states they want to
"improve the Authenticator Emulator to use a local vault
(e.g., TPM-based) to store a UID protected by a secret
or biometrics" just as we're doing. In fact, Intel has
discontinued SGX
so the credential manager must be migrated to a TPM anyway.



\subsection{Formal Analysis of the TPM and FIDO}

The Fast IDentity Online (FIDO) framework consists of two specifications: 
Universal Authentication Framework (UAF) and Universal 2nd Factor (U2F). For this project,
we will be focusing on using UAF as a way to log into a Linux system with a TPM acting like the
FIDO authenticator. According to Haonan Feng et al. \cite{9930658}, the base standard for UAF is defined with an extremely strong security model,
to the point of being impractical, so most implementations do not follow the standard strictly.

    When analyzed under a more realistic scenario, there are some practically viable 
vulnerabilities in the protocol that can be exploited. One example of such an 
attack is a transaction tampering attack \cite{9930658}, which the paper did not provide a 
solution to. However, according to Shao et al. \cite{https://doi.org/10.1049/iet-ifs.2016.0005}, the TPM supports using HMAC to encrypt and validate communication between 
itself and the CPU which could be a viable 
solution to this particular type of attack. Analysis of the security of the HMAC authorization
mechanism in the paper reveals that the implementation is sufficiently secure under most 
conditions \cite{https://doi.org/10.1049/iet-ifs.2016.0005} and therefore gives us a base for 
designing our threat model. 

    In another study by Bindel, et. al ~\cite{bindel2023fido2ctap21webauthn2}
the authors formally analyze FIDO2's security with the CTAP 2.1 and WebAuthn 2 sub-protocols. The authors prove post-quantum security for
FIDO2 under certain conditions and minor protocol extensions, and show a simple improvement for the downgrade resilience of FIDO2.
Since the paper is an abstract proof of
CTAP and WebAuthn, the authors do not model some of the new CTAP 2.1 features for enterprise
customers, and do not make formal statements about the unlinkability of credentials or other detailed privacy statements.
Thus, the implementation of these standards may have unaddressed vulnerabilities.

\subsection{TPM-Attest: Hardware-Rooted Integrity Attestation as a Kernel-Level Anti-Cheat Alternative for Linux \cite{gedela2026tpmattesthardwarerootedintegrityattestation}}

While the main focus of this paper is leveraging hardware backed boot verification as an anti-cheat
for video games on Linux, the concepts discussed can be applied to any traditional secure boot 
setup because both of these applications have the same goal: To stop unauthorized and unverified
code from executing at boot. This paper proposes using the Linux Integrity Measurement 
Architecture (IMA) alongside the TPM to gather all the information needed to validate the kernel
that is currently running. One thing this paper fails to include is being able to stop the kernel if an error is detected in integrity measurement, or ideally, a self-healing procedure if 
integrity is compromised. While we can use this as a base for verified boot, we would have to 
combine this idea with something like dm-verity in Linux to make this a complete solution.


\subsection{Attacks against FIDO authenticators}

Windows Hello is Microsoft's implementation of the Fast IDentity Online (FIDO) protocol. Kim et. al ~\cite{https://doi.org/10.1155/2021/6245306}  and Lee et. al ~\cite{11391923}
analyze the architecture of Windows Hello. Lee et. al model an adversary that only has temporary but physical access to the device under malicious (theft) or otherwise benign (repair) conditions. Firstly, Windows 11's transition to TPM is lazy - that is, though required by the OS, the TPM may not actually be utilized to store secrets, which may violate application assumptions allow credential extraction. In addition, biometrics, even with a secure transport layer with the biometric chip, are shown to be vulnerable when the biometric details are stored without proper authentication codes. Kim et al. discuss the architecture of signing onto Windows, especially with online Microsoft-linked accounts, detailing the key derivations and decryption steps from PIN to decryption of user secrets in Windows. Kim et al. specifically do not consider the TPM, and one of their key attacks centers around brute-forcing the user's PIN.

Trust Dies in Darkness ~\cite{shakevsky2022trust} by Shakevsky et. al details the architecture of Samsung's TrustZone Keymaster. Samsung implements a two-pronged solution in which a secure world and a normal world are kept separate by a secure monitor. The authors discovered certain devices were vulnerable to downgrade attacks. The possibility of a downgrade attack should be modeled and addressed in any implementation. In the TrustZone architecture, each key blob stored in KeyMaster was derived from hardware-bound master key salted by the application identifiers and other constants using AES-GCM. The hardware security module was controlled by the secure world. However, an endpoint was incorrectly exposed to the normal world which allowed access to encryption with the master-key AES-GCM cipher, while also allowing specifying the IV (the salt). Thus, an IV reuse attack could be used, breaking the AES-GCM cipher. This could then allow FIDO passkeys to be copied from the secure chip. We learn from this paper that access to the TPM should be carefully exposed and well-guarded.

\subsection{Adoption, Implementation and Usage of Passkeys}

Farke et. al ~\cite{281252} is an early study (relative to passkeys) from 2021 that investigates the deployment in a small business, and employees' sentiments on the adoption of Biometric and PIN-based authentication. Windows Hello for Business was used as the platform. It finds that users prefer the shorter PIN's, and the overall experience (including biometrics) was perceived as quicker. The participants in the study expressed some doubts that biometric data could leave the machine. One of the key findings of this early study was that Windows Hello passkeys were resident (bound) to the device - they could not roam like physical keys - and were thus unsuitable for shared computers. Reittinger and Pernul ~\cite{11573563} publish a more modern 2026 study, in a diverse passkey environment as implementations evolved over time. They investigate the challenges in adoption and use of passkeys, finding that users still perceive
passkeys superior to passwords. Reittinger and Pernul recommend a dedicated passkey management UI and clarity in where passkeys are stored (e.g. cloud-backed v.s bound to device)

In The State of Passkeys: Studying the Adoption and Security of Passkeys on the Web ~\cite{jannett2026stateofpasskeys} the authors perform a comprehensive
security evaluation of passkey implementation in websites.
The authors identify lack of standardization and serious
security issues in a majority of websites, including use
of deprecated cryptographic algorithms and critical or
high CVSS scores. The authors present
\texttt{PASSKEYS-RADAR} for tracking deployment of
passkeys on the web, and \texttt{PASSKEYS-ATTACKER} for
exploting security vulnerabilities on insecure sites.

Though these studies are relatively diverse, they have a recurring theme: transparency. In the one case, Windows Hello technology
can choose to not use TPM-backed security without indication. In the other, whether passkeys are synchronized to the cloud or local-only
is confusing. We must consider a design that is explicit about the capabilities of the passkeys it stores, and furthermore, can denote it
remains on a older security standard should future security protocols become standardized. Finally, we note that users, generally, have positive sentiments towards passkeys, both in PIN and biometric forms, as well as in actual use: continuing to bring better passkey support
to Linux is not a fruitless endeavour.


\subsection{TPM in Verified/Measured Boot}
Arbaugh et al. first introduced the "chain of trust" idea for booting a computer \cite{arbaugh1997secure}. Their core argument was to securely verify the integrity of the next layer before handing over control, and code execution halts with a recovery mechanism in case of an integrity check failure. This has evolved into modern-day Secure/Verified Boot. While Secure Boot blocks the execution of an untrusted layer, Sailer et al. proposed an alternative: measuring every loading step from boot loader to application layer inside TPM-protected logs, so that it can be verified later through TPM-backed attestation. This is known as Measured/Trusted Boot \cite{sailer2004design}. Parno et al. \cite{parno2010bootstrapping} draw a contrast between these two schemes and discuss how Trusted Computing is put to practical use, such as sealing secrets in a trusted boot state, like in BitLocker, as well as letting a verifier remotely check a device's log through TPM attestation.

A recent use case was introduced by Woltjen et al. on the Raspberry Pi \cite{woltjen2026trustworthy}. They identified that the Raspberry Pi has only the capability for Secure Boot, but not Measured Boot due to the absence of TPM driver support. The authors addressed this limitation by integrating U-Boot into the Raspberry Pi to connect with TPM 2.0, and thus combining both Secure and Measured Boot to enable Remote Attestation on the platform.
