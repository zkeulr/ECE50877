\section{TPM for Linux Authentication}

% This proposal originates with the authors of 
% \href{https://privsec.dev/}{privsec.dev} and is 
% paraphrased from their article on 
% \href{https://privsec.dev/posts/linux/linux-insecurities/}{insecurities in Linux}.

\paragraph{Title:} TPM for Linux Authentication 

\paragraph{Problem Definition:} Operating systems like Android, iOS, macOS, and Windows
use of a hardware security module for many functions, such as secure credential storage,
biometric unlock, and verified / measured boot.

On Linux, it is rather the opposite. Out of the box, most 
systems only have at best secure boot enabled (with a shim),
and perhaps somes user applications store keys in the TPM (a 
hardware security module available on most modern x86 systems). On some
configured systems, keys are stored in the TPM to unlock an encrypted disk.

While apps on linux can store credentials on the TPM, this is typically
of limited utility, as they tend not to involve user-authentication.
The situtation on other operating systems is different. On iOS, apps can
easily store credentials in the system store, which users can unlock securely
using biometrics. For example, on Windows, password managers can securely stash
a long and complex master password (used to first unlock the password database)
into a system store - then allowing users to unlock the password database using
biometric credentials later.


These facilties require a trusted operating system, for which many solutions exist.



\paragraph{Proposed Methodology:} We will evaluate the use of hardware
security modules on other mainstream operating systems, and primarily
on Windows the TPM, as it most cleanly maps to a linux solution.

We will identify current shortcomings and enumerate some attacks against
the out-of-box linux experience

We will then investigate the authentication facilities on linux, and determine
if a TPM-based solution can fit within the constraints of those facilities, or
whether a new userspace API is required.

We will then investigate the inteface provided by modern TPMs, and define an interface
between the TPM and a userspace API. Then, both pieces will be implemented. We deliberately
do not attempt to solve every bug in this implementation, and instead plan to produce
a proof of concept.

We will then test the previously enumerated attacks against the new implementation.



\paragraph{Expected Findings:} We hope to document how other mainstream operating
systems manage user authentication and secrets. We believe that by securing 
keys in a hardware security module, we will be able to defend against certain attacks
without drastically impacting the user experience, and unlock a new avenue for user applications
to store secrets and run-time.

\section{Differential Timing Analysis for 
Cryptographic Library Fingerprinting}

This proposal originates with Dr. Zahra Ghodsi of Purdue University. 

\paragraph{Title:} Differential Timing Analysis for Cryptographic Library Fingerprinting

\paragraph{Problem Definition:} The starting step of exploitation is
determining the target's technology stack. An important part of
this process is identifying the cryptographic libraries and
implementations running on the target. Existing tools can often
identify software through explicit version information or protocol
behavior, but such information may be unavailable or intentionally
hidden. This motivates the following research question:
Can differential timing analysis identify the cryptographic library
and version used by a remote target, despite network and system
noise?

\paragraph{Proposed Methodology:} We will construct a testbed
containing multiple implementations and versions of commonly used
cryptographic libraries. We will first collect
timing measurements while each implementation performs a controlled
suite of cryptographic operations under different inputs and
configurations. We will analyze the resulting timing distributions
to identify features that distinguish implementations.
We will then train and evaluate statistical and machine-learning
classifiers using these timing features.

\paragraph{Expected Findings:} We expect the number of samples 
required to train accurate classifiers to rise substationally 
with noise. We also expect machine learning classifiers to 
outperform statistical classifiers, indicating broader applicability 
of machine learning techniques to side channel analysis.
